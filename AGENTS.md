# Work Life Balance: требования и порядок разработки

Этот файл является спецификацией проекта и инструкцией для работающих в репозитории агентов. Пользовательские уточнения имеют приоритет; при изменении согласованного поведения обновлять этот документ. Разработка разделена ровно на четыре итерации. Создание этого файла само по себе не является разрешением начинать реализацию.

## 1. Назначение и согласованные решения

Локальная Windows-утилита автоматически считает время работы, отдыха и отсутствия пользователя (AFK). Приложение работает в фоне в пользовательской сессии, управляется из трея и через веб-интерфейс. Открытый браузер или фокус на интерфейсе для учёта и хоткея не нужны.

- Стек: C# / .NET, ASP.NET Core, SQLite; React, TypeScript и Vite для интерфейса; Recharts для графиков; Firefox WebExtension для браузерной активности.
- Перед реализацией выбрать поддерживаемые стабильные версии, проверить совместимость и зафиксировать зависимости и lock-файлы. Не использовать плавающие версии.
- Основной адрес: `http://127.0.0.1:47831`. Порт настраиваемый. При конфликте не завершать чужой процесс и не выбирать другой порт молча: показать понятную ошибку и способ изменить настройку. Учёт по возможности продолжает работать без веб-сервера.
- В установленной версии .NET-приложение раздаёт собранный frontend. Node.js и Vite нужны только для разработки. Итоговая поставка не должна требовать установки Node.js; предпочесть self-contained сборку для поддерживаемой Windows-архитектуры.
- Все данные остаются на компьютере. Нет облака, аккаунтов, телеметрии, внешних API, CDN, удалённых шрифтов и автоматических сетевых проверок обновлений.
- Уточнение 24.09.2026: это личный инструмент пользователя, отдельного production-развёртывания нет. Пользователь разрешил сразу применять проверенные изменения к запущенному экземпляру. Не заниматься отдельной релизной оптимизацией, упаковкой и публикацией без запроса. Сборка для локального обновления разрешена; перед заменой сохранить копию данных, штатно остановить трекер и после запуска проверить настройки, учёт и Firefox. Разрушительные тесты по-прежнему выполнять только на отдельной базе.
- Продукт измеряет активность приложений, а не реальную продуктивность. Автоматический анализ смысла страниц, AI-классификация, скриншоты, запись клавиш и содержимого страниц не входят в задачу.

## 2. Правила учёта времени

### Активное приложение

- Учитывать только окно на переднем плане и связанный с ним процесс. Открытый в фоне Blender не должен приносить рабочие часы.
- Начальный интервал опроса — примерно одна секунда. Ошибка на границе переключения ограничена частотой опроса; не обещать точность до миллисекунд.
- Последовательные наблюдения одинаковой активности объединять в интервалы. Не хранить каждую секунду отдельной строкой без необходимости.
- Рабочие приложения определяются редактируемым списком правил. Начальные примеры: `blender.exe`, `Unity.exe`, `devenv.exe`, `Code.exe`; пользователь может удалить любое правило.
- Остальные приложения по умолчанию относятся к отдыху. Отсутствующие или недоступные сведения об окне обозначать явно, не приписывать их предыдущему приложению без ограничения по времени.
- Идентичность процесса для правила не должна зависеть от PID. Базовое сопоставление — имя executable без учёта регистра; точный путь может служить уточнением правила.
- AFK и пауза учёта имеют приоритет над категорией приложения. Ручное исправление истории имеет приоритет над автоматической категоризацией приложений.

### Автоматический AFK

- Порог по умолчанию — 30 минут. Настройка принимает длительные значения, включая два часа и больше; автоматический AFK можно отключить.
- Использовать системное время последнего ввода, не перехватывая содержимое клавиш или текст пользователя.
- До достижения порога текущий интервал предварительно относится к работе или отдыху.
- При достижении порога перевести в AFK весь промежуток с последнего ввода, включая уже записанные интервалы и границы дней. Например: последний ввод в 14:00, порог 30 минут, обнаружение в 14:30 — AFK начинается в 14:00.
- Пересчёт истории и итогов выполнять атомарно, без наложения интервалов и двойного учёта. Пока пользователь остаётся AFK, продолжать тот же период отсутствия.
- Реальный ввод завершает автоматический AFK. Первое наблюдение после возврата начинает новую активность.
- Изменение порога во время текущего простоя переоценивает текущий период; не переписывает произвольно завершённые дни. Уже подтверждённый AFK автоматически обратно в работу не переводить.

### Ручной AFK и хоткей

- Глобальное сочетание: `Win + Shift + N`. Работает при любом активном приложении, пока фоновая утилита запущена.
- Если пользователь активен, хоткей включает ручной AFK с момента нажатия, без ретроспективного изменения предыдущего времени.
- Ручной AFK сохраняется при движении мыши и вводе; завершается повторным хоткеем или явным действием в трее/интерфейсе. Это предотвращает немедленный выход из AFK из-за самого нажатия хоткея.
- Если уже включён автоматический AFK, хоткей завершает его. Отсчёт следующего простоя начинается с явного возврата; нельзя немедленно снова включить AFK по устаревшему системному замеру.
- Отделять фактический последний ввод от отметки явного возврата. Не подменять системные сведения искусственным вводом.
- При паузе учёта хоткей не возобновляет сбор скрытно: сообщает, что учёт приостановлен. Состояние паузы видно во всех элементах управления.
- Если регистрация сочетания запрещена Windows или оно занято, показать ошибку и позволить назначить другое сочетание. Не заявлять гарантированную доступность Win-сочетания до проверки на целевой системе.
- Регистрация выполняется без глобального перехвата всех клавиш. После полного выхода из программы хоткей не работает, отдельный помощник для запуска не нужен.

### Уведомления Windows

- При ручном включении/выключении AFK показывать нативное уведомление с текущим статусом.
- При автоматическом входе/выходе из AFK также показывать уведомление. Для ретроспективного входа указывать фактическое начало AFK.
- Уведомлять один раз на переход, а не на каждый опрос. Не показывать очередь устаревших уведомлений после сна или разблокировки; сообщать актуальный итоговый статус.
- Уважать системные настройки уведомлений. Их блокировка не должна ломать учёт; текущий статус всегда доступен в трее и интерфейсе.

### Сон, блокировка и остановка

- Блокировка и сон немедленно прекращают начисление активного времени. Известные интервалы отсутствия отражаются как AFK; пауза учёта остаётся паузой.
- После сна сверять состояние, а не начислять весь разрыв последнему приложению. Ручной AFK сохраняется до явного выключения.
- После аварии завершать неподтверждённый интервал на последней надёжно сохранённой отметке. Периоды, когда трекер не работал, отображать как пробелы данных, не выдавая их за AFK или отдых.
- Использовать UTC для хранения моментов времени и монотонный источник для измерения прошедших длительностей внутри процесса. Изменение часов Windows не должно создавать отрицательные длительности.
- Границы календарных дней и отчёты вычислять в явно выбранном часовом поясе, по умолчанию системном. Учитывать DST и дни не по 24 часа.

## 3. Процессы, Firefox и исправления

### Редактор рабочих процессов

- Показывать обновляемый список запущенных приложений; текущее активное приложение выделять.
- По умолчанию показывать пользовательские приложения с окнами, предусмотреть просмотр остальных процессов. Недоступные системные процессы не требуют запуска всего трекера с правами администратора.
- Группировать экземпляры одного приложения; десятки PID Firefox не должны засорять список.
- Добавлять приложение в рабочие и удалять из рабочих непосредственно из списка.
- Поддержать ручной ввод executable для незапущенного приложения. Валидировать значения, предотвращать дубликаты, сохранять настройки после перезапуска.
- При изменении правила предлагать область применения: будущее время либо также существующая история. Ручные исправления не перезаписывать при автоматическом пересчёте.

### Firefox

- Расширение обязательно входит в первую поставку по завершении четырёх итераций.
- Сохранять интервалы активных вкладок: URL, домен, заголовок и время. Не собирать все фоновые вкладки или историю браузера целиком.
- Учитывать вкладку только при активном окне Firefox. При нескольких окнах брать вкладку именно сфокусированного окна. Переключения вкладок, навигацию, закрытие окна и потерю соединения обрабатывать явно.
- Любая браузерная активность по умолчанию — отдых, в том числе документация и обучающие видео. Автоматические правила по смыслу сайта не нужны. Это поведение приоритетнее обычного правила процесса Firefox.
- Пользователь может добавлять и удалять рабочие сайты. Совпадение домена или его поддомена автоматически относит новые посещения Firefox к работе. URL при вводе нормализуется до домена (IDN → ASCII, без регистра, пути, query и fragment); похожие чужие домены не совпадают. Изменения списка не переписывают прошлую историю. Приватные/неизвестные вкладки остаются отдыхом; AFK и ручные правки приоритетнее. Пересчёт правил приложений не меняет сохранённые категории сайтов.
- Пользователь вручную относит выбранные браузерные интервалы к работе или отдыху в истории; доступно разделение интервала и массовое изменение выделенных записей.
- Воспроизведение видео само по себе не отменяет AFK. Для двухчасового просмотра пользователь увеличивает порог или отключает авто-AFK. Отдельный режим просмотра сейчас не требуется.
- Если расширение отсутствует или связь потеряна, продолжать учитывать Firefox как приложение с неизвестной вкладкой и категорией «отдых». Показывать состояние подключения; не подставлять старый URL в новые интервалы.
- Приватные окна по умолчанию не раскрывают URL и заголовки: отражать только приложение/приватную активность, если её можно определить. Не требовать доступ к приватным окнам для работы расширения.
- URL могут содержать секреты: удалять userinfo и fragment, по умолчанию не сохранять query-параметры. Дать понятную настройку детализации: домен либо URL с путём. «Сохранять всё» здесь означает все наблюдаемые периоды активности, не содержимое страниц и не секреты из адресов.
- Выбрать и документировать локальный транспорт расширения: предпочтительно Native Messaging; loopback HTTP допустим с привязкой устройства/секретом и проверкой источника. Логику учёта не помещать в расширение.
- Проверить требования Firefox к установке и подписи расширений. Временная установка для разработки не считается готовой постоянной поставкой. Сетевое подписание при выпуске не должно передавать пользовательскую историю; работа установленного продукта полностью локальная.

### Ручное редактирование истории

- Разрешить смену категории целого интервала или его части, включая ошибочно определённый AFK.
- Сохранять исходные наблюдения и пользовательские поправки раздельно, чтобы можно было отменить исправление и пересчитать отчёты.
- Пояснять в деталях записи источник категории: правило приложения, браузер по умолчанию, автоматический/ручной AFK либо ручная правка.
- Не менять границы наблюдений молча. При разделении сохранять суммарную длительность и непересекающиеся части.

## 4. Интерфейс и управление

- Главный экран — рабочая статистика, не рекламная страница. Показывать текущую активность и статус трекера.
- За день: работа, отдых, AFK, доля работы среди активного времени `работа / (работа + отдых)`, лента интервалов, разбивка по приложениям и график по часам. При нулевом знаменателе показывать отсутствие данных вместо NaN.
- Паузы и пробелы данных не включать в активное время. Отличать предварительное время до AFK-порога от окончательной статистики в деталях.
- Месячная календарная сетка в духе GitHub: каждый день — квадрат, насыщенность зависит от абсолютного времени работы. Шкала фиксированная между месяцами, с легендой.
- По наведению/фокусу показывать дату и итоги, по клику открывать статистику дня. Отдельно отображать ноль работы, отсутствие данных и будущие дни.
- Переключение месяцев, итоги месяца и недельные сводки. Изменения истории сразу отражаются во всех графиках.
- Настройки: рабочие процессы, AFK, хоткей, порт, автозапуск, хранение данных и детализация браузерной истории.
- Трей: открыть интерфейс, переключить AFK, пауза/возобновление, настройки, полный выход. Состояние видно по подсказке/индикации трея.
- Второй запуск открывает интерфейс уже работающего экземпляра; не создаёт второго писателя в базу.
- Интерфейс на русском. Клавиатурная навигация, подписи для иконок, доступный контраст, состояние не обозначается одним цветом.
- Предсказуемая плотная компоновка, без декоративных карточек внутри карточек, маркетинговых блоков и чрезмерных скруглений. Использовать библиотеку иконок, например Lucide.
- Проверять desktop и узкие экраны: нет перекрытий, обрезанного текста и скачков размеров при обновлении данных.

### Дополнение: задачи на день (25.09.2026)

- Между верхней статистикой и календарём расположен список «Дела»: одноразовые задачи с названием (1–240 символов) и трудозатратностью 1–5, по умолчанию 1. Вес влияет на цвет строки/значка, но не на часы работы.
- Сегодня доступны создание, изменение названия/веса/плановой даты, удаление и отметка выполнения. Выполненные остаются в том же списке; снятие отметки сегодня убирает задачу из рекапа и возвращает в открытые.
- Будущие дни доступны для планирования и редактирования, но не для досрочной отметки выполнения. Прошлые дни показывают только выполненные в тот день задачи, исключительно для чтения; это ограничение проверяется на сервере.
- Незавершённые задачи автоматически показываются на текущий день, если плановая дата прошла. Нет дубликатов на прошлых днях; перенос работает через полночь и после любого простоя приложения. Отдельный фоновый таймер переноса не нужен.
- Дата выполнения фиксируется по локальному дню сервера вместе с UTC-моментом выполнения. После завершения дня запись не меняется. Смена часового пояса не переносит уже завершённые задачи между рекапами.
- Квадрат календаря разделён вертикально: слева часы работы (прежняя зелёная шкала), справа сумма весов выполненных задач (синяя шкала: 0, 1–4, 5–9, 10–14, 15+). Плановые задачи не окрашивают будущие дни. Подсказки содержат число выполненных и суммарный вес.
- Задачи хранятся локально отдельно от интервалов, входят в SQLite-копии и экспорт выполненного. Восстановление v4 возвращает все задачи; восстановление старой v3 оставляет текущие задачи нетронутыми. Удаление истории удаляет выполненные задачи диапазона, но сохраняет открытые планы.

## 5. Архитектура и границы модулей

Один локальный продукт и один основной процесс; микросервисы не нужны. Разделить код по ответственности, не вводя абстракции ради количества слоёв.

Предлагаемая структура:

```text
src/
  WorkLifeBalance.Domain/          # Интервалы, категории, правила, AFK-переходы
  WorkLifeBalance.Application/     # Сценарии учёта, исправлений и отчётов
  WorkLifeBalance.Infrastructure/  # SQLite, миграции, настройки, резервные копии
  WorkLifeBalance.Windows/         # Окна, ввод, сессия, хоткей, трей, уведомления
  WorkLifeBalance.Host/            # Композиция, lifecycle, loopback API, static UI
  web/                            # React/TypeScript
extensions/
  firefox/                        # Наблюдение вкладки и локальный транспорт
tests/                            # Unit, integration, UI и контракты
docs/                             # Сборка, архитектура, протокол, ручные проверки
```

- Domain не зависит от Win32, ASP.NET, SQLite или React. Application зависит от Domain и узких контрактов нужных внешних возможностей.
- Windows и Infrastructure реализуют эти контракты. Host собирает зависимости и управляет жизненным циклом.
- Изолировать источники времени, foreground-активности, idle, событий сессии, browser-сигналов, хранилище и уведомления. Это позволяет тестировать алгоритмы без настоящих окон и ожидания 30 минут.
- Один координатор последовательно обрабатывает события и изменяет учёт. Не допускать конкурирующих записей из таймера, хоткея, API и расширения.
- Отделять состояние присутствия (активен/авто-AFK/ручной AFK), состояние сбора (идёт/пауза) и классификацию (работа/отдых). Описать таблицу переходов и приоритеты в тестах.
- Канал наблюдений: источник → нормализованное событие → координатор → интервалы/поправки → отчёты → API/UI. UI не реализует собственный алгоритм подсчёта времени.
- Контракты браузерного протокола и API версионируются. Проверять формат, размер и актуальность входных сообщений; старые и повторные сообщения не должны начислять время повторно.
- Изменения истории и относящихся к ним проекций транзакционны. Агрегаты — пересчитываемые проекции, а не единственный источник истины.
- Миграции схемы последовательные и версионированные; перед потенциально разрушающей миграцией резервная копия. Никакого автоматического удаления базы при ошибке миграции.
- Базу и настройки хранить в каталоге данных пользователя, отдельно от executable и исходников. Не коммитить настоящую историю в Git.

## 6. Качество кода, приватность и эксплуатация

- C#: nullable reference types, явная обработка ошибок и отмены, освобождение native handles и регистраций. Не блокировать поток трея операциями БД или сети.
- TypeScript: strict mode, типизированные API-контракты, отсутствие необоснованного `any`. Форматирование и линтер проверяются командами проекта.
- Небольшие модули и явные зависимости. Никакого глобального изменяемого состояния для учёта, пустых catch и копий классификатора во frontend.
- Комментарии объясняют причины и инварианты; публичные контракты документируют единицы времени, часовые пояса и семантику границ. Интервалы трактуются как `[start, end)`.
- Все длительные операции ограничены отменой/таймаутом. Фоновая ошибка источника не должна незаметно выключать остальные источники.
- Логи локальные, с ротацией; по умолчанию без URL, заголовков, токенов и иных чувствительных данных. Ошибки доступны для диагностики, но не создают бесконечный поток уведомлений.
- Сервер слушает только loopback, без LAN-доступа. Проверять Host/Origin и защищать изменяющие запросы от CSRF; не включать wildcard CORS. Loopback сам по себе не является авторизацией.
- Не загружать страницы и favicon по сохранённым URL. Недоверенные заголовки отображать как текст, не HTML. SQL параметризован; входные данные валидируются на сервере.
- Экспорт CSV/JSON по запросу, локальные резервные копии и явное удаление выбранной истории. Для CSV учитывать формульную инъекцию. Полное удаление данных требует осознанного подтверждения в UI.
- Приложение работает без администратора. Установка, регистрация уведомлений, автозапуск и Native Messaging настраиваются на уровне пользователя, где это возможно.
- На каждой итерации давать воспроизводимые команды сборки/запуска/проверок, обновлять документацию и указывать реальные ограничения. Не выдавать mock-данные за работающий трекер.

## 7. Четыре итерации

### Итерация 1. Надёжный учёт, AFK и Windows-интеграция

Задачи:
- Создать solution, модульные границы, конфигурацию, базовые миграции и тестовую инфраструктуру.
- Реализовать foreground-сборщик, интервалы, рабочие правила и SQLite-хранилище.
- Реализовать регулируемый автоматический AFK с ретроспективным пересчётом, ручной AFK, паузу, сон/блокировку и аварийное восстановление.
- Добавить трей, единственный экземпляр, глобальный хоткей и Windows-уведомления.
- Поднять loopback API на выбранном порту и минимальный реальный экран состояния с настройкой AFK и списка рабочих процессов.

Критерий завершения:
- На настоящей Windows можно переключать приложения и AFK, закрыть интерфейс и убедиться, что учёт/хоткей продолжают работать.
- Укороченным тестовым порогом воспроизводится точный ретроспективный перенос времени; уведомления приходят один раз на переход.
- Тестами покрыты границы порога, ручной/автоматический AFK, пауза, отсутствие двойного учёта, полночь, сон и восстановление.
- Проверены занятый порт и недоступный хоткей; ограничения регистрации уведомлений документированы.

### Итерация 2. Firefox, процессы и редактирование истории

Задачи:
- Создать Firefox WebExtension и защищённый локальный транспорт, экран подключения и инструкции установки.
- Связать события вкладок с активным окном; обработать несколько окон, потерю связи и приватность.
- Завершить список процессов, группировку, ручное добавление/удаление рабочих executable и область применения правил.
- Реализовать хранение ручных поправок, разделение интервалов, массовую смену категории и отмену исправления.
- Добавить дневную ленту и список истории на реальных данных.

Критерий завершения:
- Firefox автоматически считается отдыхом; пользователь может выделить просмотр урока и перевести его в работу.
- Фоновая вкладка не начисляет отдельное время, потеря связи не продолжает старый URL, повторные сообщения не дублируют интервалы.
- Исправления сохраняются после перезапуска и пересчёта правил. Тесты проверяют сохранение длительности и приоритет ручных правок.
- Проверен путь постоянной установки расширения; оставшиеся внешние требования к подписи названы явно.

### Итерация 3. Полный dashboard и календарь

Задачи:
- Завершить дневные показатели, почасовой график, приложения по длительности и обновление без перезагрузки.
- Реализовать месячную сетку активности, фиксированную шкалу, подсказки и переход к выбранному дню.
- Добавить месячные и недельные итоги, навигацию по датам и пустые/ошибочные состояния.
- Завершить настройки, доступность и адаптивную компоновку.

Критерий завершения:
- Числа dashboard, календарь и детализация согласованы после AFK-пересчёта и ручных правок.
- Ноль, отсутствие данных, будущие дни, паузы и текущий неполный день различаются корректно.
- Автотесты проверяют отчёты на фиксированных данных, DST и границы месяца. UI проверен на desktop и узком экране, в том числе снимками браузера.

### Итерация 4. Поставка, приватность и проверка end-to-end

Задачи:
- Подготовить self-contained поставку, автозапуск, постоянную установку Firefox-расширения и инструкции обновления/удаления.
- Реализовать экспорт, резервное копирование/восстановление и управление сроком хранения без тихой потери данных.
- Проверить миграции, повреждённую/недоступную базу, аварийный выход, перезапуск Windows, конфликт порта и регистрацию хоткея.
- Проверить отсутствие исходящих запросов продукта и утечек чувствительных данных в логи. Зависимости UI поставляются локально.
- Провести длительный прогон, оценить CPU, память, рост базы и периодичность записи; зафиксировать результаты, не придумывать показатели.
- Завершить пользовательскую документацию и описание архитектуры/протоколов.

Критерий завершения:
- На целевой Windows приложение запускается без dev-сервера и Node.js, работает в фоне, открывает локальную статистику и сохраняет данные после перезапуска.
- Firefox устанавливается постоянным поддерживаемым способом; временная debug-установка не выдаётся за законченный релиз.
- Сквозной сценарий проходит: работа в приложении → браузер → авто-AFK с пересчётом → возврат → ручной AFK хоткеем → правка истории → календарь → перезапуск.
- Выполнены значимые unit/integration/UI-проверки. То, что требует ручной проверки Windows/Firefox, отмечено отдельно с результатом, а не объявлено проверенным по сборке.

## 8. Порядок работы агента

1. Перед изменениями прочитать существующий код, этот файл и состояние Git. Не удалять и не откатывать чужие изменения.
2. Работать в рамках запрошенной итерации; общий план не является разрешением на публикацию, установку сертификатов или отправку файлов во внешние сервисы.
3. До редактирования кратко сообщать, что меняется. При выборе библиотек и системных API сверять актуальную официальную документацию.
4. Сначала фиксировать контракты и инварианты нужного сценария, затем реализовывать минимальный законченный путь через backend и UI. Не оставлять обязательное поведение за mock-реализацией.
5. Покрывать рискованные алгоритмы осмысленными тестами с подставным временем. Не использовать реальные получасовые ожидания и тесты, лишь повторяющие реализацию.
6. Выполнять сборку, линтеры и релевантные проверки. Отдельно проверять нативные сценарии на Windows; браузерный тест не подтверждает работу Win32-хоткея.
7. В финале итерации сообщать, что работает, какие проверки выполнены, какие ограничения остались и какие команды позволяют воспроизвести результат. Обновлять документ при согласованном изменении требований.

## 9. За пределами согласованного объёма

- Синхронизация между устройствами, облачные аккаунты и удалённый доступ.
- AI-детектор полезности, содержимое страниц, скриншоты и запись ввода.
- Автоматическая классификация по смыслу сайта и признание видео работой без явно заданного пользователем доменного правила.
- Другие браузеры и ОС; архитектура допускает новые адаптеры, но их реализация сейчас не нужна.
- Учёт по проектам, блокировка отвлекающих приложений, достижения и система штрафов.
- Отдельный помощник, ловящий хоткей после полного выхода из приложения.

## 10. Состояние реализации

Реализован код итераций 1–4: учёт, Firefox, правки, dashboard, self-contained .NET 10 win-x64, автозапуск, установка/удаление, экспорт CSV/JSON, SQLite-копии и восстановление истории, подтверждаемая очистка. Срок хранения сохраняется как предпочтение для ручного подтверждения очистки; фонового удаления нет. Восстановление сохраняет текущие настройки. Копии не удаляются автоматически. Результаты: `docs/iteration-1.md` — `docs/iteration-4.md`; руководство: `docs/user-guide.md`. Полная приёмка итерации 4 ещё требует длительного прогона, перезагрузки/автозапуска и установки/удаления в обычной сессии; не выдавать эти проверки за выполненные.

Firefox 0.2.0 подписан с разрешения пользователя; постоянная установка и подключение подтверждены пользователем (`docs/firefox-signing.md`). Регистрацию NativeHost выполнять из обычной PowerShell: реестр среды агента оказался невидим обычному Firefox. Новые внешние публикации не разрешены автоматически. Готовая сборка теперь находится в `.artifacts/release`; старую `.artifacts/app` не удалять, пока пользовательский Firefox использует зарегистрированный там помощник.
